# Лабораторная работа №2

Модульные, интеграционные и сквозные тесты VitaLine Clinic на постоянном Docker-стенде. Отчёты — Allure.

## Запуск

Команды выполняются в WSL из `lab2`. Нужны Docker Compose, Python 3 и Make.

```bash
make setup
make up
make test
```

`setup` собирает образ с Go, Allure и Delve. После изменения Dockerfile или `scripts/container.sh` образ нужно пересобрать.

Постоянно работают MongoDB, API и сервер отчётов:

- [Отчёты запусков](http://localhost:8093).
- [Проверка постоянного API](http://localhost:8094/health).
- `make status` — состояние контейнеров.
- `make down` — явная остановка стенда; данные и отчёты сохраняются.

`make test` также проверяет готовность стенда. Этапы: **unit ЛР1 → integration → e2e**. Следующий этап запускается только после успешного предыдущего. После тестов постоянный стенд продолжает работать.

Каждый прогон получает новое имя автоматически. Можно задать своё:

```bash
make test RUN_ID=tester-01
```

Имя должно быть новым: до 64 строчных латинских букв, цифр и дефисов. Повторное использование существующего имени отклоняется. Это защищает результаты другого тестировщика.

## Параллельные тестировщики

```bash
make parallel
```

Команда поднимает стенд при необходимости и запускает пять полных прогонов одновременно. Она проверяет разные базы, успех всех этапов, очистку сессий и пересечение запусков во времени. Другое количество можно задать через `COUNT`, например `make parallel COUNT=2`.

Во втором терминале из того же каталога выполните:

```bash
make parallel-logs
```

Команда автоматически выбирает логи последней группы параллельных прогонов и показывает их обновления. Ctrl+C останавливает только просмотр логов. В Allure на http://localhost:8093 появятся пять отдельных отчётов с одинаковым префиксом `parallel-...` и окончаниями `-1` … `-5`. После завершения у каждого должны быть три статуса `passed`.

Автоматические контейнеры запускаются без TTY и без чтения stdin (`-T --interactive=false`); фоновые процессы не останавливаются сигналом SIGTTIN. Пока прогон выполняется, ещё не запущенные этапы в списке отчётов обозначены «ожидает». Если предыдущий этап упал, последующие остаются `skipped`.

Общие ресурсы — постоянно работающая MongoDB, сервер отчётов и кеши Go. Каждый запуск получает:

- отдельную базу `lab2_<хеш RUN_ID>`;
- отдельный экземпляр API из зафиксированного снимка исходников;
- собственную Docker-сеть, контейнеры тестов и каталог `reports/<RUN_ID>`;
- собственную резервную копию базы и состояние в `.runs/<RUN_ID>`.

Постоянный API на порту 8094 использует базу `lab2_stand`. Тесты обращаются к своей копии API: так тестировщики могут менять данные и отлаживать код, не затрагивая соседние прогоны и демонстрационный API.

Запуски не сериализуются целиком. Блокировки защищают запуск общего стенда, публикацию списка отчётов и операции с одним RUN_ID. Порты API сессий наружу не публикуются; порт Delve назначается отдельно каждой сессии.

## Allure и падения

Откройте [список запусков](http://localhost:8093), затем нужный отчёт. В **«Тест сьюты»** этапы сгруппированы как модульные, интеграционные и сквозные тесты.

Отчёт пересобирается после каждого этапа и при завершении, включая ошибку или SIGTERM. Пока прогон идёт, открытая страница обновляется раз в 10 секунд. HTML заменяется атомарно: браузер не получает наполовину записанный файл. Завершённые отчёты сохраняются отдельно.

Готовый `reports/<RUN_ID>/index.html` можно открыть двойным щелчком без сервера.

Виджет «Тренд» показывает текущий прогон и до 19 предыдущих завершённых прогонов из `reports/`, включая падения. История упорядочена по началу запуска; незавершённые сессии и прогоны, закончившиеся после начала текущего, в неё не входят. Поэтому параллельный тестировщик не добавляет в график частично записанные результаты. Старые отчёты сохраняют историю на момент своего запуска.

Для проверки настоящего падения Go-теста после HTTP-регистрации пациента:

```bash
LAB2_E2E_FAIL=1 make test
```

Команда завершится с ошибкой. В Allure будут красными e2e-тест и запись об ошибке этапа; это две записи об одном учебном сбое. Unit и integration останутся зелёными. Тестовый флаг не меняет код приложения.

Проверка остановки конвейера после integration:

```bash
LAB2_FAIL_STAGE=integration make test
```

Интеграционные тесты выполнятся, затем этап завершится учебной ошибкой. E2E будет пропущен. По умолчанию после сбоя выполняются восстановление и очистка только своей сессии.

## Отладка e2e

Для нового сеанса:

```bash
make debug RUN_ID=debug-01
make debug-connect RUN_ID=debug-01
```

Первая команда создаёт изолированную базу, запускает API и Delve. Вторая открывает консоль отладчика. Go-код теста находится внутри контейнера в `/src/lab2/e2e/`; отладочный бинарный файл собирается без оптимизаций.

Пример команд в Delve:

```text
break /src/lab2/e2e/patient_journey_e2e_test.go:60
continue
print base
print p.ID
next
continue
exit
```

Строка 60 — начало создания записи, после успешной регистрации пациента. На этой точке можно увидеть адрес API и выданный ID. После изменений файла уточните номер строки через `list TestPatientJourney`.

Для IDE команда `make debug` печатает свободный локальный порт. Настройте remote attach к `127.0.0.1:<порт>` и соответствие локального каталога `lab2` пути `/src/lab2`.

Чтобы сохранить состояние именно упавшего прогона:

```bash
LAB2_E2E_FAIL=1 LAB2_KEEP_FAILED=1 make test RUN_ID=failed-01
make debug RUN_ID=failed-01
make debug-connect RUN_ID=failed-01
```

База и API сохраняются; журналы и Allure доступны. Delve запускает тест заново на сохранённой базе. Учебный флаг `LAB2_E2E_FAIL` действует только для команды, перед которой задан: для повторения того же сбоя в отладчике укажите его также перед `make debug`.

Ручная отладка не переписывает результаты автоматического теста. После исправления запустите новый `make test`.

Завершите консоль Delve и очистите свою сессию:

```bash
make recover RUN_ID=debug-01
# либо RUN_ID=failed-01
```

Постоянный стенд и другие сессии останутся работать.

## Тесты и диагностика

| Файл | Сценарий |
|---|---|
| `integration/patient_repository_integration_test.go` | Создание, чтение, изменение, удаление пациента; повторный email |
| `integration/appointment_service_integration_test.go` | Запись, занятое время, отмена и повторная запись |
| `integration/schedule_filter_integration_test.go` | Свободные слоты по врачу и дате |
| `integration/visit_service_integration_test.go` | Завершение визита, история, повторное завершение |
| `e2e/patient_journey_e2e_test.go` | Регистрация → запись → визит → история через HTTP |

В ЛР2 четыре интеграционных сценария и один e2e; моки в них не используются. Модульные тесты берутся из ЛР1. Счётчик Allure включает родительские Go-тесты и записи об ошибках конвейера.

В карточку e2e приложены вывод теста, журналы контейнеров и HTTP-трафик. Захват начинается **до e2e**, поэтому PCAP сохраняется и при падении теста. Если API не успел запуститься, трафика ещё нет — причину смотрите в журнале контейнера.

| Файл в `reports/<RUN_ID>` | Содержание |
|---|---|
| `index.html`, `summary.json` | Allure и состояние прогона |
| `<этап>/junit.xml`, `events.jsonl` | Проверки, ошибки, вывод Go |
| `traffic/demo.pcap`, `decoded.txt` | Трафик e2e и его текстовая расшифровка |
| `traffic/requests.txt` | Дополнительный успешный сценарий через curl |
| `containers.log` | Журналы API и служебных контейнеров |
| `rollback.txt`, `cleanup.txt` | Восстановление и очистка сессии |
| `source.txt`, `images.txt` | Снимок исходников и версии Docker-образов |

В Wireshark откройте PCAP, задайте фильтр `http`, затем **Follow → TCP Stream**.

## GitHub Actions

Workflow находится в `../.github/workflows/lab2.yml` относительно `lab2`. Каталог `.github` должен находиться в корне GitHub-репозитория рядом с `lab1`, `lab2` и `project`.

Для запуска зарегистрируйте в настройках GitHub-репозитория **Settings → Actions → Runners → New self-hosted runner** один Linux x64 runner с меткой `tiopo-lab2`. На его машине должны быть Docker Compose, Python 3, Make и Git; пользователь runner должен иметь доступ к Docker. Рабочий каталог runner должен сохраняться между сборками. Не размещайте несколько runner с разными checkout на одном Docker-стенде: его bind mounts привязаны к постоянному пути проекта. Для демонстрации одновременных тестировщиков используйте `make parallel` на этом стенде.

Workflow запускается при push изменений исходников или вручную через **Actions → Lab 2 - tests and Allure → Run workflow**. Отдельные шаги: сборка инструментов, подготовка, unit, integration, e2e. После ошибки следующие тестовые шаги пропускаются; статусы предыдущих этапов дополнительно проверяет `pipeline.py`. Шаги завершения сессии и загрузки артефактов используют `always()`: при обычном падении тестов сохраняются Allure HTML, JUnit, логи и трафик. Жёсткое завершение runner может потребовать ручного `make recover RUN_ID=...`.

Каждый запуск имеет уникальный `RUN_ID=gha-<run_id>-<attempt>`. Checkout сохраняет незакоммиченные каталоги отчётов и сессий (`clean: false`); не добавляйте `lab2/reports/` и `lab2/.runs/` в Git. Постоянный стенд после сборки остаётся поднятым. Отчёт доступен через сервер на машине runner и как скачиваемый артефакт сборки GitHub. История виджета «Тренд» берётся из сохранённых локальных отчётов.

Для демонстрации блокировки e2e при ручном запуске выберите `fail_stage=integration`. Для настоящего падения Go e2e-теста включите `fail_e2e`. Поле `fail_stage` вызывает учебную ошибку после реальных тестов выбранного этапа.

Это CI для проверки приложения на тестовом стенде. Публикация приложения в production в workflow не настроена.

## Восстановление и Jenkins

`make repeat` выполняет два последовательных прогона. `make check-interruption` прерывает подготовку e2e сигналом SIGTERM после записи контрольного документа и проверяет восстановление.

Перед integration выполняются миграция и `mongodump`. После этапов база своей сессии восстанавливается через `mongorestore`; отпечатки документов и индексов должны совпасть. В конце удаляются только эта база и контейнеры сессии. Постоянные контейнеры, тома и кеши сохраняются.

После SIGKILL или отключения Docker выполните `make recover RUN_ID=...`. Не удаляйте `.runs/<RUN_ID>` незавершённого прогона: там находятся снимок кода и резервная копия базы.

```bash
make ci
make ci-run
make ci-stop
```

Jenkins: [localhost:8092](http://localhost:8092), задание `tiopo-lab2`, логин `student`, пароль в `ci/.env`. Настроены два исполнителя. Jenkinsfile выполняет те же этапы и всегда публикует JUnit, Allure HTML и артефакты; постоянный стенд после сборки сохраняется. Отчёт открывается через общий сервер или скачивается из артефактов сборки.

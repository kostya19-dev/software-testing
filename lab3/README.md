# Лабораторная работа №3 — микробенчмаркинг

Сравнение двух библиотек стандартной поставки Go: `encoding/json` и `encoding/gob`.
Три сценария (запись, чтение, запись + чтение), два размера сообщения (4 и 64 записи),
100 независимых испытаний **каждой из 12 комбинаций**.

## Быстрый просмотр результата

Готовый эксперимент хранится в [evidence](evidence/README.md).
Откройте `evidence/report.html` локально в браузере: графики встроены в HTML,
интернет и сервер не нужны. GitHub показывает HTML как исходный файл; скачайте его.
Исходные измерения сохранены в `evidence/raw.jsonl.gz`, условия — в `manifest.json`,
таблицы — в `statistics.csv` и `summary.json`.

## Запуск

Нужны Linux или WSL, Go 1.23+, Python 3.10+, Make, работающий Docker Engine/ Docker Desktop
с Linux-контейнерами. Программа бенчмарка использует только стандартную библиотеку Go.
На машине эксперимента использован Go 1.27.3; для точного повторения используйте эту версию.
Версия компилятора и настройки сборки сохраняются в каждом отчёте.

Для отчёта нужны matplotlib и numpy. Можно использовать уже установленные пакеты
или установить закреплённые версии в отдельное окружение Python 3.10/3.11:

```bash
cd lab3
python3 -m venv .build/venv
.build/venv/bin/pip install -r requirements.txt
make test PYTHON=.build/venv/bin/python
make smoke PYTHON=.build/venv/bin/python
make run PYTHON=.build/venv/bin/python
```

В используемой WSL зависимости уже есть, достаточно:

```bash
cd lab3
make test
make smoke
make run
```

- `make test` — проверки кодеков, фаз, формул статистики и целостности результатов.
- `make smoke` — 2 испытания по 32 операции на фазу: проверка запуска, **не** зачётный эксперимент.
- `make run` — 100 испытаний по 256 операций на каждую фазу.
- `make run TRIALS=200 CPU=2 ITERATIONS=512 SAMPLES=512` — изменение параметров.
  Число испытаний чётное, не меньше 100. Для всех испытаний одного запуска параметры одинаковые.
- `make report RESULT=results/<идентификатор>` — пересоздание отчёта из исходных данных.
- `python3 scripts/verify.py evidence` — проверка опубликованного эксперимента и его контрольных сумм.

Результаты каждого запуска сохраняются отдельно в `results/<UTC-время>-<случайный-id>/`.
Сценарий печатает `RESULT=...` и `REPORT=...`. Повторный запуск не перезаписывает результаты.

`CPU=0` — номер логического CPU **Docker Engine**, а не Windows.
Если он недоступен вашему Docker, выберите доступный номер. Во всех случаях задаются
`--cpuset-cpus=<CPU>`, `--cpus=1` и `GOMAXPROCS=1`. Остановите собственную тяжёлую
нагрузку перед экспериментом. Другие лабораторные и контейнеры скрипт не останавливает.

## Что считается операцией

| Сценарий | Одна логическая операция |
|---|---|
| `write` | Сериализация одного заранее подготовленного объекта в новое сообщение |
| `read` | Десериализация заранее подготовленного сообщения в новый объект |
| `roundtrip` | Сериализация объекта и десериализация полученного сообщения |

Синтетические данные напоминают записи клиники, но не зависят от проекта, БД, сети
или персональных данных. В сообщении 4 либо 64 вложенные записи.
Для обоих кодеков исходные структуры одинаковы, корректность проверяется полным сравнением.
В каждой операции создаётся независимое сообщение: gob-encoder и gob-decoder не переиспользуются.
Поэтому выводы относятся к независимым сообщениям, а не к длительному gob-потоку.

## Как устроен эксперимент

1. Один раз собирается статический Go-бинарник с отключённым cgo; фиксируется SHA-256.
2. Создаётся базовый Docker-образ `FROM scratch`.
3. Для **каждого** испытания собирается отдельный образ с уникальной меткой и image ID.
   Слои с файлами и все рабочие настройки одинаковые; скрипт проверяет это через Docker inspect.
   Это именно отдельные образы, а не 100 тегов одного image ID.
4. Новый контейнер получает один закреплённый CPU, 512 MiB памяти, отключённую сеть,
   read-only rootfs, непривилегированного пользователя и неизменные настройки Go.
5. В контейнере выполняются все 12 комбинаций. Порядок сценариев воспроизводимо перемешан.
   В нечётных испытаниях JSON перед gob, в чётных — наоборот: 50 AB и 50 BA.
6. Для каждой комбинации: подготовка и проверка вне измерений, GC перед warmup,
   warmup → пакетное измерение → индивидуальные задержки → teardown.
   GC в измеряемом коде остаётся включённым; вывод на диск и сеть отсутствует.
7. Результаты и метаданные сохраняются, свой контейнер и свой образ удаляются.
   При ошибке эксперимент помечается незавершённым и не выдаётся за полный.

Параметры, source/binary SHA-256, ID образов и контейнеров, CPU, память, runtime и времена
можно проверить в `manifest.json`. Сборка, Docker-запуск, подготовка, проверки, выделение массива
для записей задержек и финальная запись JSON не включаются в время одной операции.

## Отчёт и статистика

Для каждой комбинации кодек/сценарий/размер есть:

- график отдельных задержек во времени;
- зависимость задержки от процентиля (с числом измеренных запросов);
- гистограмма всех задержек с количеством запросов по вертикали;
- p50, p75, p90, p95, p99, минимум, максимум, среднее, стандартное отклонение;
- время и количество операций отдельно в warmup, двух измеряемых фазах и teardown;
- медиана пакетного времени, 95% bootstrap-интервал и парное отношение gob/JSON.

Подробности определения фаз, накладных расходов и статистических ограничений:
[методика](docs/methodology.md). Соответствие всем пунктам задания:
[матрица требований](docs/requirements.md).

## Автоматическая проверка

Workflow `.github/workflows/lab3.yml` выполняет тесты и двухконтейнерный smoke-прогон
при изменениях ЛР3. В workflow предусмотрен `workflow_dispatch` с полным экспериментом.
Для ручного запуска через интерфейс GitHub файл workflow должен также присутствовать
в default branch репозитория; без этого полный эксперимент запускается локально через `make run`.
Времена GitHub runner не следует смешивать с временами локальной машины.
Артефакты отчёта загружаются и при ошибке; незавершённый прогон сохраняет причину.

# Лабораторная работа №1

Модульные тесты VitaLine Clinic: домен, сервисы, хранилища в памяти и адаптеры MongoDB. Приложение находится в `../project/VitaLineClinic`. Работающая база данных для ЛР1 не нужна.

**Отчёт о тестировании — Allure.** Правила и ссылки на тесты находятся в [таблице сценариев](docs/spec.md). Этот README объясняет запуск и подготовку к показу.

## Запуск отчёта

Нужны Go, Python 3, GNU Make, Java 17+ и npm. Все команды выполняются в WSL из каталога `lab1`.

При первой установке:

```bash
make setup
```

После изменения кода или перед показом:

```bash
make test
make check-docs
make show
```

`make test` выполняет тесты, сохраняет JUnit и сразу собирает HTML-отчёт Allure. `make check-docs` проверяет, что все ссылки из документации ведут в существующие файлы и на тесты, прошедшие в полном прогоне. `make show` собирает Allure и запускает сервер. Откройте адрес, напечатанный в терминале. Ctrl+C останавливает сервер отчёта.

По умолчанию используется порт 8081. Если он занят, сервер автоматически выбирает свободный порт и печатает новый адрес. Можно задать предпочтительный порт: `make show PORT=8082`. Чтобы только собрать файл без сервера, выполните `make report`.

Готовый отчёт: [reports/normal/allure/index.html](reports/normal/allure/index.html). После `make test` откройте этот файл двойным щелчком из папки; сервер не нужен. После `make clean` отчёт удаляется и появляется снова при следующем `make test`. Это один HTML-файл, его можно открыть отдельно в браузере. В нём сохранены результаты последнего прогона; `make report` сам тесты не запускает.

Скрипт `scripts/report.py` переносит результаты JUnit и описания из таблицы сценариев в [формат Allure](https://allurereport.org/docs/how-it-works-test-result-file/). HTML строит Allure CLI. Интерфейс, условия и ожидания — на русском; имена Go-тестов и пути сохранены.

## Как найти тест по документации

В [docs/spec.md](docs/spec.md) каждый раздел имеет номер **UC**, а каждая строка проверки — номер **TC**.

- **Use case:** что делает пользователь или компонент. Например, UC-06 — создание записи на приём.
- **Test case:** конкретное условие и ожидаемый результат. Например, TC-06-04 — время занято, ожидается `ErrSlotBusy`, запись не создаётся.
- **Go-тест:** исполняемая проверка этого ожидания. Для TC-06-04 это `TestAppointmentCreateErrors/busy_slot`.

Преподаватель выбирает раздел → вы находите нужную строку → открываете ссылку на файл → показываете соответствующую функцию и подтест → запускаете строку по её номеру:

```bash
make case CASE=TC-06-04
make show RESULTS=reports/cases/TC-06-04
```

Команда печатает условие и ожидание, выбирает тест из таблицы и сохраняет отдельный результат вместе с HTML-отчётом. Полный отчёт остаётся в `reports/normal/`.

В Allure:

1. Откройте **«Функциональность»** и выберите юзкейс **UC** из документации.
2. Внутри выберите тест-кейс **TC** и карточку результата.
3. Прочитайте условие и ожидаемый результат в описании.
4. Параметр **«Go-тест»** содержит точное имя функции и подтеста. Во вложении **«Исходный код»** находится соответствующий Go-файл.
5. Покажите подготовку данных, вызов метода и проверки результата. Команда повтора указана в описании.

Например: **UC-06 → TC-06-04 «Время занято» → TestAppointmentCreateErrors/busy_slot**.
Раздел **«Тест сьюты»** сохраняет техническую навигацию по пакетам.

Одна строка документации может ссылаться на группу подтестов. Например, проверка обязательных полей пациента запускает шесть случаев. Родительские функции тоже попадают в JUnit и счётчик Allure; в разделе «Функциональность» они вынесены в «Группы тестов». Поэтому число записей отчёта больше числа самостоятельных сценариев.

## Разбор трёх примеров

### Занятое время: UC-06 → TC-06-04

Откройте [usecase/errors_test.go](usecase/errors_test.go), функцию `TestAppointmentCreateErrors`.

В строке `busy_slot` заданы будущая дата, `busy=true` и ожидаемая ошибка `domain.ErrSlotBusy`. Мок метода `CheckSlotBusy` возвращает занятость.

Действие — `service.Create(...)`. После него проверяются:

```go
require.ErrorIs(t, err, tt.want)
require.Equal(t, usecase.AppointmentResponseDTO{}, result)
require.Nil(t, saved)
```

Здесь `tt.want` равен `domain.ErrSlotBusy`. Проверяется конкретная причина отказа, пустой ответ и отсутствие сохранённой записи. Тест зелёный, потому что ожидаемая ошибка получена.

### Неверный email: UC-01 → TC-01-03

В том же файле найдите `TestPatientValidationErrors`, строку `invalid_email`. Подготовка задаёт `Email="abc"`, действие вызывает `Register`.

```go
require.ErrorIs(t, err, domain.ErrValidation)
var validation *domain.ValidationError
require.ErrorAs(t, err, &validation)
require.Equal(t, tt.field, validation.Field)
```

Первая проверка подтверждает общую категорию, вторая извлекает типизированную ошибку, третья проверяет поле `Email`. Затем тест читает репозиторий в памяти и убеждается, что пациент не сохранён.

`make case CASE=TC-01-03` запускает всю группу валидации пациента. В Allure выберите внутри неё `invalid_email`.

### Фильтр свободных слотов: UC-05 → TC-05-02

Откройте [storage/memory/filter_test.go](storage/memory/filter_test.go), функцию `TestScheduleFreeSlotsFilter`.

Подготовлены четыре слота: подходящий, другого врача, другой даты и занятый. Действие — `FindFreeSlots`. Проверка требует ровно один результат с ID подходящего слота. Так проверяется включение нужной записи и исключение всех трёх неподходящих.

```bash
make case CASE=TC-05-02
make show RESULTS=reports/cases/TC-05-02
```

## Шаблон проверки ошибки в Go

В этом приложении ожидаемые ошибки операций возвращаются как `error`. Для них используются готовые утверждения библиотеки [Testify/require](https://pkg.go.dev/github.com/stretchr/testify/require).

| Проверка | Что подтверждает |
|---|---|
| `require.Error(t, err)` | Возвращена любая ненулевая ошибка |
| `require.ErrorIs(t, err, expected)` | В цепочке ошибок есть ожидаемая причина, включая обёртки `%w` |
| `require.ErrorAs(t, err, &target)` | В цепочке есть ошибка заданного типа; она записывается в `target` |
| `require.NoError(t, err)` | Успешная операция не вернула ошибку |
| `require.Panics(t, func() { ... })` | Вызов вызвал `panic`; используется для контрактов, ожидающих панику |

`require` останавливает текущий тест при неуспехе, поэтому после `ErrorAs` можно безопасно читать поле извлечённой ошибки. Сравнение через `errors.Is` и `errors.As` в остальных тестах выполняет те же проверки стандартной библиотекой.

У бизнес-методов этого проекта отказ по занятости, неверным данным или статусу выражается через `error`. Паники моков при неожиданном вызове сигнализируют о неверной настройке или поведении тестируемого кода; отдельные демонстрационные panic-тесты для них не добавляются.

## Остальные команды

| Команда | Назначение |
|---|---|
| `make test-domain` | Доменная валидация и переходы статусов |
| `make test-usecase` | Сервисы и ошибки зависимостей |
| `make test-memory` | Хранилища в памяти |
| `make test-mongodb` | MongoDB на mock-транспорте |
| `make errors` | Отдельный набор ошибок валидации, причин отказа и переходов статусов |
| `make show RESULTS=reports/errors` | Allure для набора ошибок |
| `make coverage` | Покрытие операторов и ветвей |
| `make shuffle SEED=42` | Перемешивание верхнеуровневых тестов |
| `make offline` | Прогон без внешней сети |
| `make race` | Проверка гонок |
| `make all` | Полный прогон, проверка документации, покрытие, shuffle, offline и Allure |
| `make clean` | Удаление результатов запусков |

Для нескольких пакетов: `make test SUITES="domain usecase" PARALLEL_PACKAGES=2`. Результат — `reports/normal/domain-usecase/`.

Seed воспроизводит порядок верхнеуровневых тестов при том же коде и версии Go; порядок подтестов задаётся кодом. При параллельном запуске общий порядок событий пакетов может отличаться.

## Файлы и ограничения

- `domain/`, `usecase/`, `storage/` — тесты; `testutil/testdata.go` — независимые тестовые данные и builder пациента.
- `docs/spec.md` — единственная таблица соответствия сценариев и тестов. Команда `make case` и подписи Allure читают её напрямую.
- `reports/<режим>/` — JUnit, события Go, вывод, параметры, порядок, команда повтора и процессы тестов.
- `reports/cases/<TC>/` — результаты запуска одной строки документации.
- `reports/coverage/` — профиль, HTML исходников, покрытие операторов, ветвей и экспорт Cobertura.

Область покрытия: `domain`, `usecase`, `storage/memory`, `storage/mongodb`. Метрика `line-rate` конвертера не равна доле уникальных строк всего приложения. Моки MongoDB не проверяют настоящий сервер. Границы каждого ожидания указаны в таблице сценариев.
